# P2.2B Selective Responsibility Promotion Plan

**Status:** APPROVED / CONTROLLING FOCUSED PLAN — B1 EVIDENCE SELECTION / NO PROMOTION YET  
**Date:** 2026-09-01  
**Scope:** First bounded P2.2B responsibility-promotion increment after P2.2A closure  
**Authority:** Subordinate to product/domain/source/architecture constraints, `docs/UTILITY_EPISTEMIC_AUTHORITY_AND_REASONING_POLICY.md`, `docs/ROADMAP.md`, `docs/IMPLEMENTATION_PLAN.md`, and `docs/P2_2_RESPONSIBILITY_WORK_ROLE_INTELLIGENCE_PLAN.md`

## 1. Decision

P2.2B is authorized only as a **selective responsibility-promotion pilot**.

The first increment must reuse the accepted Canonical Registry contract unchanged unless a concrete eligible responsibility correspondence proves that the current contract cannot represent it safely.

```text
accepted/current P1.6 responsibilities
→ bounded evidence selection
→ semantic review of a concrete cross-job correspondence
→ only if non-lossy and reusable: one reviewed responsibility concept + exact claim mappings
→ CLI/browser/currentness/idempotency verification
→ B1 decision
```

Do not start P2.2C responsibility families until this pilot demonstrates useful reusable responsibility authority or explicitly records that current evidence is insufficient.

## 2. Important rejected first candidate

The initially considered pair is **not approved for promotion**:

`t4qV` P1.6 artifact 44 responsibility[9]:

> Preparing technical documentation for security equipment such as Cisco Secure Firewall ...

`tmyX` P1.6 artifact 46 responsibility[3]:

> Preparing checklists, technical documentation, and security reports

Reason:

- `t4qV` is specifically technical documentation for security equipment;
- `tmyX` is compound work covering checklists, technical documentation, and security reports;
- the current registry maps one immutable P1.6 responsibility claim to one canonical responsibility concept;
- forcing both claims into a single broad documentation concept could erase source distinctions or silently treat a partial overlap as whole-claim correspondence.

This is exactly the kind of normalization loss P2.2B must avoid.

## 3. B1 objective

Prove one **genuinely reusable, non-lossy responsibility correspondence** using the existing Canonical Registry.

A successful B1 should normally produce only:

```text
1 reviewed canonical responsibility concept
2 exact accepted/current P1.6 responsibility mappings from different jobs
0 automatic aliases unless independently justified
0 deliverable promotions
```

This is a bounded proof, not a completeness target.

## 4. Eligibility rule

A responsibility pair is eligible only when all of the following hold:

1. both inputs are accepted/current English P1.6 `responsibilities[]` claims;
2. they express the same reusable responsibility identity at the canonical level;
3. differences are harmless wording, grammar, specificity that can remain source detail, or equivalent surface formulation;
4. the mapping does not discard an additional material action, object, ownership relationship, lifecycle endpoint, or compound duty from either source claim;
5. the normalized concept has a concrete downstream reuse hypothesis, primarily P2.2C family membership or later capability-profile reuse;
6. exact source wording and provenance remain recoverable from each mapping.

Do not promote merely because two statements share keywords or belong to the same broad theme.

## 5. Bounded evidence search

Current accepted responsibility-bearing jobs are too heterogeneous to force a clean pair.

The next local step is therefore a bounded search for one better recurrence:

- inspect existing current English projections / already available local job evidence first;
- prioritize jobs that can answer this specific cross-job responsibility question;
- add at most one new accepted P1.6 job if a concrete candidate requires semantic acceptance;
- do not bulk-run acceptance, mapping, or ontology expansion;
- stop once one strong pair is found or once the bounded candidate set shows no safe pair.

A new accepted job is allowed here only because the controlling P2.2 plan explicitly permits adding evidence for a concrete repeated cross-job responsibility pattern.

## 6. Existing-registry reuse

Use the existing contract:

```text
jobhunter-canonical-concept-registry-v1
```

Expected existing capabilities:

- `ConceptCategory.RESPONSIBILITY`;
- reviewed stable `responsibility:<slug>` IDs;
- exact accepted-P1.6 responsibility mapping provenance;
- immutable mapping decisions;
- currentness/stale-dependency behavior;
- idempotent reviewed mutations;
- CLI and browser inspection.

Do not create a parallel responsibility ontology or a P2.2-specific canonical store.

## 7. Deliverables are deferred from B1

The registry has a `deliverable` concept category, but the current reviewed claim-mapping identity is built around P1.6 `requirement | responsibility` claims and does not provide a reviewed mapping identity for P2.2A Work Intelligence deliverables.

Do not add deliverable schema/mapping machinery speculatively.

Reopen deliverable promotion only after a concrete repeated deliverable demonstrates downstream value and gives us an evidence-backed mapping identity to design around.

## 8. Promotion operation if an eligible pair is found

Before mutation, record the exact candidate:

```text
job A / P1.6 artifact / responsibility[index] / exact statement
job B / P1.6 artifact / responsibility[index] / exact statement
proposed responsibility:<slug>
preferred label
definition or boundary note if needed
why the correspondence is non-lossy
what downstream reuse it enables
```

Then:

1. create/reuse exactly one reviewed responsibility concept;
2. map the two exact accepted/current P1.6 responsibility claims;
3. rerun the same reviewed operations to prove idempotent reuse;
4. inspect current mappings in CLI;
5. inspect the concept and mappings in browser;
6. verify stale/current behavior remains unchanged;
7. verify no public-corpus mutation/publication occurred.

No LLM generation is required for the promotion mutation itself.

## 9. Stop / success rules

### Success

B1 succeeds when one selected responsibility identity is proven reusable across at least two accepted/current jobs without material semantic loss, and the existing registry safely persists and exposes that reviewed authority.

### No-promotion result

If the bounded search does not find a clean pair:

```text
record insufficient reusable correspondence evidence
→ create no canonical responsibility
→ create no mappings merely to make P2.2B look complete
→ decide whether P2.2B should remain deferred while job-level P2.2A intelligence continues
```

A no-promotion result is valid evidence, not a project failure.

## 10. Non-goals / stop lines

During B1:

- do not bulk-map accepted responsibilities;
- do not normalize partial semantic overlaps as whole-claim equivalence;
- do not broaden a concept merely to absorb compound claims;
- do not auto-promote P2.2A theme or deliverable labels;
- do not add deterministic verb-equivalence machinery;
- do not add responsibility families or role archetypes yet;
- do not publish registry or P2.2 state;
- do not start Market v2, personal intelligence, scoring, or recommendations;
- do not add schema/migrations unless a concrete eligible pair exposes an actual contract gap.

## 1. Proportionate orientation before work

Existing AGENTS required reading and policy hierarchy remain controlling. Orientation depth is chosen by blast radius, not number of files or duration of previous session.

| Scope | Minimum additional orientation |
| --- | --- |
| Narrow docs/tests/developer tool | Current revision, actual affected text/code/tests and relevant owner; explicitly exclude runtime/authority if unchanged. |
| Component implementation/defect | Follow public or research entrypoint to actual resolved owners and callers; inputs/output contracts, direct and active transitive dependencies, deterministic/model responsibilities, reads/writes, failure/reuse/validation, downstream consumers and currentness. Inspect relevant tests and known gaps. |
| Cross-component, storage, model contract, routing or authority change | Above plus affected producer/consumer identities, compatibility/migration/rollback, privacy/export, failure/partial/stale behavior, applicable governing decisions and owner approval gates. Trace representative success and adverse workflows; use actual offline/live evidence only where authorized. |
| Comprehensive subsystem/project orientation | Explicit inventory of included and excluded components, follow major workflows and authority boundaries, verified revision, source/test/receipt references and open unknowns. Do not say fully oriented from reading only plans, filenames, an import graph or a narrow inspection. DOC.6 extends system coverage progressively. |

Use a short orientation note in the work record where meaningful: scope/revision; entrypoints and resolved owners; data/contracts/dependencies; state/failure/authority and consumers; evidence/tests; gaps and next decision. Reuse established maps when their scope and fingerprints still match, but inspect changed and relevant uninspected paths. Distinguish current, active transitive, compatible-only, candidate, historical and proposed; distinguish static inspection, observed execution, offline tests/replay, illustration and design. Unknowns remain unknown. For minor changes, a concise note in existing record is enough; no standalone form or duplicated prose.

## 2. Change and drift procedure

1. Before modifying, check Git state and revision, current tracker and relevant governing contract. Determine affected components, paths and consumers, including active inherited code. If uncertain, inspect; no automatic import-based deletion or call conclusions.
2. For material changes, compare actual diff against affected profile/map, contract and status. A changed file is a reinspection signal, not proof of architectural change. An unchanged fingerprint is evidence of identical inspected bytes only. Use Git diffs plus targeted symbols/method resolution/tests; optional DOC.4 extraction supplies supporting evidence. Check semantic behavior separately where required.
3. Update affected **living** reference(s), navigation/status if needed, code/tests and decision record as part of the same increment. If no architecture change, say why and which boundaries were checked; do not rewrite every map or bump every timestamp. Preserve dated records/receipts and link superseding scope. Proposed A1/A2 stays separate from implemented v30/v9.
4. Reviewer checks actual resolved owner, behavior, authority and limitations; verify relevant links/identities, regressions, protected state and any open issue. No claim of comprehensive orientation or production readiness solely from static tests. Document exact revision or base + local diff identity, and whether source is dirty.
5. Before closure, ensure tracker/current-state navigation points to the next applicable gate; older milestone next-actions are historical. If drift affects authority/contract or a critical safety boundary, resolve or explicitly hold affected work before promotion. If ordinary documentation gap is outside scope, register bounded follow-up with owner/trigger. No autonomous scope expansion.

### Lightweight checks (manual/on demand)

From repository root: `git status --short --branch`, `git rev-parse HEAD`, `git diff --name-status <verified-revision> HEAD -- src scripts tests` (also inspect local working changes when present). For P1.6 optionally run `python scripts/inspect_p16_architecture.py --runtime` and compare file hashes, symbol locations, resolved owners/MRO/schema summaries against dated receipts. Inspect only reviewed frozen schema copies, never initialize production for documentation. For non-P1.6 use actual relevant entrypoints and tests rather than forcing the tool. A changed fingerprint prompts review; no universal generated architecture diff or mandatory CI drift gate. Existing tests and Ruff remain required by applicable scope. Reconsider a dedicated CI check only if repeated real drift and a stable low-noise predicate justify it. No extra third-party dependency.

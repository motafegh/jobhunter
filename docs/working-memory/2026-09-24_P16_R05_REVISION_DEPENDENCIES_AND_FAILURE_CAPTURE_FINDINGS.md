## 1. Exact current downstream identity consequences (inspected on main)

- `src/jobhunter/analysis_store.py`: non-rejected artifact uniqueness is scoped to detail/projection/model/prompt/schema (separate original and translated indexes); current and accepted-only readers select a matching analysis artifact. The existing review action handles a whole artifact. Simply inserting a second non-rejected corrected artifact under the same contract would collide. Prompt/schema identities must not be falsified to smuggle in a review revision.
- `src/jobhunter/capability_store.py` and `src/jobhunter/capability_service_v8.py`: Capability stores the exact accepted `analysis_artifact_id`, in its uniqueness key and foreign key. A different accepted analysis is a **new dependency**, not an in-place update of existing Capability. `src/jobhunter/role_blueprint_store.py` also stores analysis and Capability artifact IDs; Blueprint remains experimental, not an excuse to promote revisions automatically.
- `src/jobhunter/work_intelligence_store.py`: candidate Job Work Intelligence also keys its result to an exact analysis artifact ID. New revisions must not make old Work records appear to apply to changed claims.
- `src/jobhunter/canonical_registry.py`: `job_claim_canonical_mappings` is unique per `(analysis_artifact_id, claim_kind, claim_index)` and also stores source text. Insert/remove/reorder or change of a claim invalidates **index-based correspondence**; do not silently copy mappings by index or normalized label. Carry forward only independently verified unchanged claim/evidence identity, with explicit old-to-new index correspondence and reviewed mapping policy.
- `src/jobhunter/market_store.py`: memberships and immutable snapshot members retain exact analysis artifact IDs, and immutable triggers protect Market history. `src/jobhunter/market_aggregate_service.py` aggregates accepted-semantic core members by their frozen snapshot analysis ID. Old snapshots and profiles must never be rewritten to point at a correction. A future run/snapshot may select a separately approved new analysis only under explicit currentness/version rules.
- `src/jobhunter/public_corpus.py`: English P1.6 export queries accepted-current analysis and checks the linked translation identity; Capability export also checks exact analysis/projection linkage. Diagnostics, review annotations and unpromoted revisions must remain outside this export; a future promoted revision needs deliberately updated read/export behavior.

**Integration recommendation (not yet selected as schema):** Start with a private, separately owned diagnostic and review-annotation sidecar linked to existing attempt/artifact identities; preserve existing accepted/current queries unchanged. Store revised *draft* claim sets as separate, immutable review revisions, not ordinary accepted artifacts. Defer publication of a revised accepted payload until a targeted identity/current-selector migration explicitly solves non-rejected uniqueness, current-vs-historical selection, accepted compatibility anchors, and all exact downstream references. Do not mark a valid historical accepted artifact rejected merely to free a uniqueness slot. A sidecar-only revision must not be silently consumed by existing Capability/Market readers as if it were an analysis artifact.

## 2. Actual failed-response availability: source inspection versus local verification

- `pyproject.toml` allows `instructor>=1.15,<2`; the precise version installed in the user's local `.venv` is not established by the repository constraint. The current v21 path uses `V21CandidateAnalysisProvider` -> shared v20 `client.create_with_completion(...)` with `max_retries=1` for each bounded partition (`analysis_runtime_v21.py`, `analysis_runtime_v20.py`, `inference/instructor_lm_studio_v20.py`). On success, both validated response and raw completion are returned. On failure, the current v20 wrapper constructs `InferenceResponseError(f'...: {exc}')`; it does not return raw completion or retry metadata as a typed outcome.
- Inspected upstream **Instructor v1.15.3** source: [`instructor/v2/core/errors.py`](https://github.com/567-labs/instructor/blob/v1.15.3/instructor/v2/core/errors.py) (re-exported by [`instructor/core/exceptions.py`](https://github.com/567-labs/instructor/blob/v1.15.3/instructor/core/exceptions.py)). `InstructorRetryException` exposes `last_completion` and optional `failed_attempts` with `attempt_number`, `exception`, and optional `completion`. `IncompleteOutputException` exposes optional `last_completion`; `ResponseParsingError` exposes optional `raw_response`. These fields provide a **plausible best-effort, typed capture path**; they do not promise an actual completion on network/model-context/preflight errors, identical fields for all versions, or the original HTTP bytes. A completion object is not necessarily lossless wire-protocol content.
- **Potential confidentiality hazard from existing error plumbing:** that upstream 1.15.3 `InstructorError.__str__` can render failed-attempt exception/completion information. The v20 wrapper interpolates `exc` and `analysis_service_v20.py` passes errors into `analysis_store.record_attempt`, which persists `str(error)`; therefore model text may appear in ordinary error records. This is a source-established possible exposure route, **not a claim that a secret actually leaked**. Do not log/persist arbitrary SDK exception strings or `create_kwargs`/messages as supposedly sanitized diagnostics. Prefer typed error classification and a short bounded generic attempt message; retain any permitted original response only in a protected local diagnostic payload with explicit redaction/size/retention rules and no public-corpus/log export.
- The user's exact installed 1.x runtime, LM Studio/OpenAI-compatible completion shape, retry behavior and safe serialization remain **unverified**. Verify with local deterministic fixtures (no live generation): retry exhausted with completion, retry exhausted without completion, truncated completion, parse/schema error, earlier successful partition then later failure, post-merge failure, and an exception containing sentinel secret-like text. Assert that no sentinel appears in normal attempt messages, CLI/browser generic errors, logs, review snapshots, or public exports. Check failure diagnostic capture is best-effort and does not mask the original failure or create a pending artifact. Then consider local non-network SDK smoke tests if version behavior warrants.

## 3. Proportionality and proposed phased path

**Phase A — diagnostic safety and capture:** classify actual failures and sanitize existing generic attempt/error messages; link bounded private diagnostic records to the existing attempt ledger with source/projection/model/contract and partition-stage identity. Capture a response **only where obtained**. Keep existing artifact/store/current selector and all strict integrity/acceptance gates unchanged. Separate meaningful provider failure from structurally invalid returned data.

**Phase B — pending-candidate utility:** attach item review findings, proposed source-backed corrections, and independently anchored coverage gaps to an existing pending analysis. Extend its existing inspectable job-level view; do not introduce a second accepted-analysis pipeline or conflate review status with `concept_type`. Exact source evidence and disputed original wording remain inspectable. Diagnostic fragments remain in a visibly different, non-authoritative interface.

**Phase C — reviewed revisions and controlled promotion:** create immutable draft revision lineage and test old/new claim-index correspondence; design the minimal accepted-publication/current-selector migration across Capability, Registry, Work, Blueprint, Market and public corpus before enabling promotion. An approved semantic proposal alone does not create an accepted P1.6 artifact. Use a new accepted analysis ID for a genuinely changed payload, with historic accepted IDs and snapshots intact.

**Stop lines:** No product code, migrations, validator weakening, model calls, new candidate acceptance, v22 promotion, Market I7 status change, or publication of diagnostics is authorized by this research record. Do not assume all affected code paths have been exhaustively audited; require targeted code/test verification before designing the exact migration. The next decision is to approve or amend the *phased design*, then separately authorize bounded implementation and regression tests.
